# TLAN 内置 FRPC 后续开发路线

日期：2026-10-21。项目：`D:/RadminLanPrivate`。

本文根据《FRPC-INTEGRATION-PLAN.md》《CURRENT-CODE-VERIFICATION-2026-10-21.md》和《FRPC-DESKTOP-COVERAGE.md》整理。当前状态以最新验证报告为准；本文描述后续建议、交付范围和验收要求，不表示这些改造已经完成。本文未重新执行代码测试，也未修改业务代码。

## 1. 产品目标与下一阶段重点

将 TLAN 做成统一管理虚拟组网与服务发布的 Windows 客户端：用户可以只组网、只做 FRP 穿透，也可以在明确授权后发布组网成员的指定服务。界面延续现有原生 GUI，功能之间的启停、权限和故障边界必须清晰。

当前已经接通主要协议和真实 FRPC/FRPS 链路，不需要推倒重写。下一阶段应优先解决“运行行为是否符合用户意图”和“两个网络部件是否真正隔离”，之后再扩展协议、后台运行和配置能力。

建议采用以下交付顺序：

1. 建立可追溯基线，修复已确认缺陷。
2. 完成双向网络冲突检查、实际出口约束和资源清理。
3. 完成真实双机、实际 Linux 部署和长时间验收，交付基础稳定版本。
4. 补齐常用配置与诊断体验。
5. 按需求推进后台服务、权限分离、升级机制和高级协议。

下文使用 R0—R5 表示新的开发里程碑，与原方案 P1—P4 功能阶段区分，避免把“P3 主体已实现”误认为“P3 已完成所有验收”。

## 2. 必须保持的产品边界

| 边界    | 必须满足的行为                                                |
| ----- | ------------------------------------------------------ |
| 网卡所有权 | 只有 Mesh 部件创建和管理 TLAN 虚拟网卡、组网路由；FRP 不启用 VirtualNet      |
| 独立发布  | 指向回环和经批准的非 Mesh LAN 目标的 FRP 配置不因关闭组网而停止                |
| 成员发布  | Mesh 服务必须经过 TargetGateway，绑定网络、设备、服务和当前有效代次；依赖失效后关闭转发  |
| 控制通道  | FRPS 连接不得经过 TLAN 自身虚拟网络或依赖本产品发布入口形成循环；遵循合法的系统/VPN 出口策略 |
| 权限变化  | 删除、禁用、撤销和收紧权限后，失败恢复不得重新扩大发布范围                          |
| 操作意图  | 等待、重试和后台恢复均可取消；用户明确停止后不能自行重新发布                         |
| 原有身份  | 不因 FRP 改造重置已有入网身份、密钥或虚拟地址                              |
| GUI   | 沿用现有配色、控件、间距和交互；普通用户不用编辑 TOML、管理子进程或理解内部租约             |

“参考项目全部功能”应转为逐项能力清单。VirtualNet、任意可执行核心、任意插件和未经校验的配置透传，与原方案存在直接冲突，不应列为稳定版必做事项。若将来确有这些需求，应单独修订产品边界和设计，不在导入或高级选项中悄悄放开。

## 3. R0：建立基线和验收机制

目标：让后续改动可以追踪、复现和回退。

- 检查忽略规则，排除凭据、运行时配置、日志、临时二进制和构建缓存；建立经过审查的 Git 初始基线。目前验证记录显示仓库文件尚未跟踪，不能依赖现有 Git 历史恢复代码。
- 保存固定 FRP 版本、来源、平台、摘要、许可证、Go 工具链、构建参数及能力表，构建不自动选择 latest。
- 将审计目录中的六项失败探针整理为正式回归测试。保留真实 FRPC 回滚复现，避免只断言内部字段；其他测试按可移植性拆分。
- 分离纯模型测试、Windows 管理器测试和真实核心集成测试。修复 F-07 后，将两平台构建、静态检查和各自原生测试纳入 CI。
- 为每项需求记录设计章节、实现入口、测试、证据和状态：未实现、已实现未验收、已验收、有意不支持。

验收：新环境可以按文档重复构建；提交与产物对应；现有通过项保持通过；失败探针形成明确待修任务。Linux 原生执行不能由 Windows 上的交叉编译替代。

## 4. R1：修复已经确认的逻辑缺陷

优先处理 F-01、F-02、F-04；F-05、F-06、F-07 可在同阶段完成。F-03 涉及实际网络约束，纳入 R2，不应以补一个 CIDR 判断结项。

| 工作项               | 改造要求                                             | 验收要求                                       |
| ----------------- | ------------------------------------------------ | ------------------------------------------ |
| F-01 更新失败重开旧映射    | 引入配置差异和权限集合判断；收紧/删除先撤销；失败只允许恢复仍被新权限允许的部分，否则停止相应组 | 删除旧规则并添加失败规则后，旧入口不再可达；禁用、凭据变更、保存失败、进程失败均覆盖 |
| F-02 无法取消等待/失败    | 状态快照区分运行意图、实际进程和可用操作；任何保留运行意图的状态都提供停止/取消         | 依赖断开→等待→用户停止→依赖恢复，不能自动重开；失败后可以解除身份切换阻塞     |

| F-06 visitor 依赖混用 | 立即将 visitor 纳入依赖分类；当前单进程配置先拒绝不兼容组合，并引导拆分配置       | 独立 visitor 不随无关 Mesh 停止；非法组合能明确说明原因        |
| F-07 平台测试约束       | Windows Manager 测试放入 Windows 文件；可移植模型测试保留跨平台     | Windows/Linux 静态检查通过；各自原生测试与构建通过           |

### 4.1 配置事务设计

建议区分“用户期望配置”“当前生效配置”“待应用修订”和“发布权限上限”。每次变更有修订号；取消、异步重试和旧回调不得覆盖新修订。

处理流程：校验新配置 → 计算权限变化 → 持久化必要的撤销意图 → 撤销不再允许的入口 → 应用仍被允许的新运行配置 → 确认注册与状态 → 更新生效记录。

这里的撤销意图必须能跨进程异常退出保留，避免本次内存中已经撤销，重启后却按旧磁盘配置恢复。若必要记录无法持久化，应停止相关运行并禁止静默自动恢复，明确要求用户处理。实现时需定义持久化故障下的恢复协议，不能只改一个 rollback 分支。

完整旧配置回滚只适用于不违反新权限上限的情况。认证、授权目标、端口、域名、visitor 监听范围、服务身份均需要参与比较。复杂权限比较无法确定时，默认停止受影响的组，保留诊断信息。

### 4.2 状态与并发约定

建议沿用并整理现有状态：停止、启动中、运行、等待依赖、重试退避、停止中、失败。另行暴露 DesiredRunning、CanStop、当前修订号、依赖原因及错误类型，名称可随现有代码调整。

- 用户停止先清除运行意图，再取消重试、续租和等待任务，最后回收资源。
- 不可重试错误结束运行意图；可重试错误保留意图，但必须可取消。
- Profile 内操作串行化，异步结果核对运行代次，防止 Start/Stop/Apply 相互覆盖。
- 身份切换只阻止真正依赖旧身份的运行；独立配置不应无理由阻塞入网操作。
- GUI 通过线程安全快照读取状态，后台任务不直接读写 GUI 或 Mesh 可变字段。

R1 出口条件：相关负向回归通过，现有本机真实 FRP 联调不退化。R1 完成仍不意味着“无网络冲突”。

## 5. R2：完成虚拟组网与 FRP 的协调层

这是产品稳定性的核心开发方向。保留现有独立进程和 Manager，按职责提取协调能力，不为目录命名做大规模重构。

| 能力                 | 职责                               | 实现注意点                                  |
| ------------------ | -------------------------------- | -------------------------------------- |
| RuntimeCoordinator | 串行协调 Mesh/FRP 启停、身份切换、依赖暂停与恢复    | 管操作关系，不接管现有 Mesh 数据面                   |
| NetworkObserver    | 维护接口、地址、有效路由、服务器解析结果及网络变化快照      | 区分 TLAN、其他 VPN、物理接口；快照带代次              |
| ConflictPlanner    | 在启动前和运行变化后形成允许、拒绝、暂停及解释          | Mesh 启动和 FRP 启动双向检查；无足够证据时不宣称路径安全      |
| EndpointRegistry   | 记录管理口、visitor、目标网关、Mesh 控制端口及其归属 | 动态端口也登记；仍需实际 bind/系统检查，注册表不能代替 OS 端口仲裁 |
| TargetPolicy       | 统一目标分类、保留地址、授权集合及跨配置检查           | 保存、启动、更新复用同一规则                         |
| ResourceLedger     | 记录本进程拥有的子进程、接口、路由、规则、监听和清理结果     | 不按名称或地址相似度删除其他应用资源                     |

### 5.1 F-03 的完整处理要求

1. 解析 FRPS 服务器地址，对实际候选目的地址查询有效路由；支持多地址，并明确 IPv4/IPv6 的支持边界。不能只检查服务器字符串或默认路由。
2. 拒绝经 TLAN 接口到达的 FRPS 目的地址，并识别本产品控制和发布入口之间的已知依赖循环。无法识别的外部级联要明确能力边界，不承诺检测所有互联网环路。
3. 启动 Mesh 前评估拟创建接口和路由对运行中 FRP 的影响；冲突时阻止本次操作并说明对象，不静默改变正在运行的出口。
4. 网卡重建、Wi-Fi/有线切换、第三方 VPN、休眠恢复、域名变化和路由变化后重新评估；去抖并使用代次检查，避免旧事件恢复新状态。
5. 合法第三方 VPN 路径应得到尊重；不通过增加默认路由、修改 DNS 或强行选择物理网卡来绕过它。
6. 明确检查与实际 socket 的一致性：预检查通过后，FRPC 再次解析域名或系统改路由可能使结果失效。事件通知和重新检查是必要条件，但不能独自证明没有竞态窗口。

### 5.2 先验证出口约束是否需要 worker

用固定核心做一个独立技术验证，确认受管官方二进制在当前接入方式下，能否同时满足：实际目的地址受约束、源接口/地址受约束、TLS serverName 正确保留、重连仍受约束、网络变化后不回退到 TLAN。

若现有固定核心接口无法提供足够控制，应提前引入原方案中的独立 `tlan-frpc-worker`，或经评估采用可覆盖实际连接的操作系统约束。worker 保持独立模块和进程，只增加必要的连接适配，继续复用官方 FRP 协议实现。

不能因为 worker 最初列在 P4，就把已经属于基础要求的出口隔离推迟。反过来，也不应在没有验证缺口之前直接替换全部运行框架。worker 的控制通道 hook 不等于覆盖所有数据连接、visitor、UDP 或未来打洞流量；新增能力必须逐条列出拨号入口并验证。

### 5.3 按依赖域隔离运行

建议依赖分类至少包含：独立回环/非 Mesh LAN、绑定指定 Mesh 网络的发布，以及未来单独定义的其他类型。visitor 同样参与分类。

短期继续采用一个 Profile 对应一个受管进程，并拒绝不兼容的混合依赖。中期如果确需让用户在一个配置页面管理混合规则，再由协调器拆分多个运行组；在此之前不引入多组事务、配额、日志聚合的额外复杂度。

Mesh 目标继续经过 TargetGateway。成员替换、公钥变化、虚拟 IP 被重新分配、网络代次变化、授权失效时，要关闭旧连接/UDP 会话并重新验证；禁止改走物理 LAN 上碰巧同地址的主机。

### 5.4 清理和异常恢复

修复 Mesh Close 忽略 cleanup 错误的问题。对清理失败保留资源归属与错误，界面说明残留及影响，重试须幂等。异常退出后只能回收能证明属于本产品对应实例的资源，不能按进程名结束所有 frpc 或删除相同网段的其他路由。

R2 出口条件：策略模型测试、网络事件故障注入和真实虚拟接口路径验证均通过；不能仅以“已增加观察器类”验收。

## 6. R3：真实场景验收与首个基础稳定版

R1/R2 通过后再进入发布验收。允许提前搭建测试环境，但不能用环境准备完成代替功能达标。

最低测试环境：两台独立 Windows 客户端、一台实际 Linux FRPS/控制面服务器、可控制的物理 LAN 服务、可切换的网络路径。真实游戏验收应选择用户实际使用的游戏，不能把普通 TCP/UDP 回显成功等同于游戏发现功能正常。

| 场景                  | 需要的证据                                 |
| ------------------- | ------------------------------------- |
| 只开 Mesh、只开 FRP、同时运行 | 双向业务连通、资源归属、两者状态分别准确                  |
| 关闭 Mesh             | 独立 FRP 继续工作；Mesh 发布及时关闭；用户停止后不自动恢复    |
| FRPC 崩溃或 FRPS 不可达   | Mesh 正常；重试可取消、无无限进程增长；状态与原因清楚         |
| 接口重建、休眠、VPN/路由变化    | FRPS 不走 TLAN；合法系统出口得到尊重；恢复需重新验证       |
| 成员地址与 LAN 地址重叠      | Mesh 发布不回退到同 IP 的物理设备；结合抓包和实际业务证明     |
| 删除规则、撤销授权、服务端故障     | 已撤销入口不重开；既有 TCP 和 UDP 会话符合定义的停止时限     |
| 身份/网络切换             | 无旧凭据、旧网关、旧租约和旧代次继续转发                  |
| 端口占用与多个 Profile     | 冲突在操作前给出可理解提示；不影响无关配置                 |
| 实际 Linux 安装/升级/重启   | 服务可运行，权限和配置正确，失败恢复可复现                 |
| 24—72 小时混合负载        | 记录内存、句柄、进程、重连、租约、错误及资源回收趋势            |
| GUI 实际可见测试          | 沿用原风格；中文缩放和常见 DPI 下无截断；状态、停止按钮和错误反馈准确 |

性能和时限指标必须先测基线再冻结。记录带宽、延迟、抖动、丢包、CPU、内存、句柄和恢复时间；以相同环境的 Mesh 单独运行、FRP 单独运行作为比较基线。当前本机撤销测试的十秒内结果是已测证据，不是所有公网环境的保证。联网撤销与控制面断连后的租约到期应分别定义边界和验收。

首个基础稳定版范围建议：现有六类代理、visitor、多配置、受控 LAN、托管授权和已验收的 Mesh 目标发布。某项高级联动未通过真实路径验收时，不应标记稳定；可保持实验性关闭，但必须公开说明未达成范围，不把范围收缩写成原方案全部完成。

## 7. R4：补齐常用功能与统一操作体验

稳定性门槛通过后，优先增加减少操作成本的功能。

| 功能           | 方向与前置条件                                                    |
| ------------ | ---------------------------------------------------------- |
| 受限配置导入/导出    | 导入先解析成 TLAN 模型，预览差异、逐项报告不支持内容；不直接执行外部 TOML；默认导出不带秘密        |
| 规则复制、排序、批量创建 | 批量展开为可审核的明确规则，受统一配额、目标和端口策略约束；不盲目提高现有限额                    |
| HTTP 常用配置    | locations、访问认证、subdomain、请求/响应头等按固定版本字段、授权和真实 vhost 测试逐项开放 |
| 诊断导出         | 汇总版本、脱敏配置、状态时间线、路由判定、端口冲突、租约与网关错误；不导出 token、私钥和 capability |
| 发布可用性反馈      | 区分核心运行、代理注册、后端可达和真实外网探测；只有完成对应检查才显示对应结论                    |
| 成员服务授权体验     | 展示谁发布了谁的哪个服务，提供撤销和历史；是否要求目标成员逐次确认作为单独产品决策                  |

GUI 建议继续复用现有卡片、列表、按钮和字体。普通操作围绕“服务器、目标服务、发布入口、启动/停止”组织；租约代次、接口索引等放入诊断。错误提示包含原因和可执行的解决动作，例如“目标属于当前虚拟网络，请改用成员服务发布”。

必须明确 STCP/SUDP 访问需要相应访问端，UDP 映射并不自动提供二层广播发现，HTTP/HTTPS 的证书终止与本地后端协议也要在实际配置中说清楚，避免界面暗示超出能力。

## 8. R5：长期演进

### 8.1 常驻与权限分离

按顺序推进关闭窗口行为设置、托盘、自启动，再决定是否需要无人登录的 Windows 服务。每步都定义谁拥有运行意图、退出是否停止、注销是否继续、如何取消自启动。

建议长期将普通 GUI、低权限 FRP worker 和需要高权限的 Mesh 操作分离。通过受限 IPC 传递明确操作，校验调用者与资源归属。后台服务场景需重新设计用户 DPAPI 凭据归属，不能直接假设 SYSTEM 服务可解密当前用户秘密。此项是独立设计与迁移任务。

### 8.2 核心升级与供应链

提供受控版本切换而非任意二进制替换：版本能力矩阵、来源与摘要验证、发布签名策略、配置迁移、升级前检查、失败恢复及服务端兼容验证。程序版本回退仍必须遵守最新权限上限，不能连同旧发布权限一起恢复。

### 8.3 高级协议

XTCP、QUIC、KCP、WebSocket/WSS、tcpmux 按真实使用场景排序；不把协议数量当作完成度。每增加一种能力，都要补充连接路径、独立端口、身份授权、依赖域、网络变化、退出清理和性能验收。XTCP 等涉及额外打洞路径，不能套用现有 TCP 控制连接验证结论。

### 8.4 服务端部署产品化

借鉴 stilleshan/frpc 的部署便利性，完善自有安装、升级、服务配置、运行诊断和恢复说明。客户端核心集成与 Docker/NAS/Linux 客户端部署属于不同交付范围，后者根据需求另立任务，不能因参考了仓库就宣称已经覆盖。

## 9. 开发批次与执行建议

建议按以下可独立审查的批次推进；具体工期需要结合开发人数、网络环境和 R2 技术验证结果估算，不在缺少依据时承诺日历日期。

| 批次 | 内容                    | 完成标志                           |
| -- | --------------------- | ------------------------------ |
| A  | 基线、正式失败测试、平台测试拆分      | 失败可复现、构建可追溯                    |
| B  | 配置事务、运行意图、停止/取消       | F-01/F-02 回归通过，重启恢复不突破权限       |

| D  | 实际出口约束技术验证            | 明确固定核心是否足够、是否提前需要 worker，并形成证据 |
| E  | 网络观察、双向协调、资源账本        | F-03 完整解决，变化和清理行为可测            |
